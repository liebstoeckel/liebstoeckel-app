A plugin's shared state is a typed schema mapped onto a Yjs structure, so concurrent edits from many devices merge automatically.

## The schema

Build state shapes with `schema`/`t`:

```ts
import { schema, t, type Infer } from "@liebstoeckel/plugin-sdk";

const pollSchema = schema({
  question: t.string,
  options: t.array(t.string),
  votes: t.record(t.string),  // participantId → chosen option
  closed: t.boolean,
});
type PollState = Infer<typeof pollSchema>;
```

| Builder | Type | Yjs mapping |
| --- | --- | --- |
| `t.string` `t.number` `t.boolean` | primitives | plain values |
| `t.array(item)` | `T[]` | `Y.Array` |
| `t.record(value)` | `Record<string, V>` | `Y.Map` (concurrent-friendly) |
| `t.object({…})` / `schema({…})` | nested object | `Y.Map` |

The schema gives runtime validation, a default value, and static types via `Infer`.

## The PluginState API

`ClientProps.state` is a typed accessor over the shared doc:

```ts
state.snapshot();                      // current state as plain JS (defaults filled in)
state.set("closed", true);             // replace a whole top-level field
state.recordSet("votes", pid, "Yes"); // set one entry of a record field
state.recordDelete("votes", pid);      // remove one entry
state.ensureDefaults({ question, options }); // seed once, only if empty
const off = state.subscribe((snap) => …);    // observe deep changes
```

<Aside type="caution" title="The one-level record rule">
`recordSet` / `recordDelete` operate on a **top-level** record field, one key deep. There is no nested-record setter. Model all concurrent-write state as top-level `t.record(...)` fields keyed by **composite strings**.
</Aside>

For example, the Q&A plugin needs per-question, per-participant votes. Rather than nesting, it keys a flat record by `` `${questionId}|${participantId}` ``:

```ts
const qaSchema = schema({
  questions: t.record(t.object({ text: t.string, author: t.string, ts: t.number })),
  votes: t.record(t.boolean),     // key: `${qid}|${pid}`
  answered: t.record(t.boolean),  // key: qid
  dismissed: t.record(t.boolean), // key: qid
});
```

Then derive views with pure functions (`rankedQuestions`, `voteCount`, …) that you can unit-test without a browser.

## Seeding from author props

The presenter typically seeds initial content from the placement's `props`, once:

```tsx
useEffect(() => {
  if (p.role === "presenter" && p.snapshot.options.length === 0) {
    p.state.ensureDefaults({ question, options });
  }
}, [/* … */]);
```

`ensureDefaults` is a no-op once the state is non-empty, so it's safe to run on every presenter render.

## Before the session state arrives

A page that joins a live session starts with an empty shared state and gets the session's state from the server a moment after it connects. Until then, `snapshot` holds only your schema's defaults: no votes, no questions. Writing into that empty state would race the session's real one (seeding defaults could replace the votes already cast), so the engine holds every write made through `state` back until the session state has arrived, then makes them in order. `ensureDefaults` then checks against the real state, and a `recordSet` adds to the existing record.

Your plugin gets a `synced` prop, `false` in that moment and `true` otherwise (always `true` outside a live session). Show a "connecting" state while it is `false` rather than empty results, which a presenter reloading their tab would read as lost votes:

```tsx
if (p.synced === false) return <Card><Eyebrow>Results · connecting…</Eyebrow></Card>;
```

Writes that go around `state` (directly on `doc`) are not held back; keep them for data only your plugin writes.

## Ephemeral state

For transient effects (e.g. reactions floating up), store entries in a record keyed by `crypto.randomUUID()` and **prune** old ones on a timer with `recordDelete`, plus a per-participant rate limit. This converges across clients and keeps the doc small without needing a separate awareness channel.

## Limits on audience writes

When you present through the relay, it bounds what the audience can write into a plugin's `audienceWrites` fields, whatever the plugin's own schema allows:

| What | Limit |
| --- | --- |
| Entries in a field that holds only single values (strings, numbers, booleans), like poll votes or Q&A upvotes | 50 000 |
| Entries in a field that holds any object, like Q&A questions or reactions, and in any container nested inside an entry | 10 000 |
| Length of a string or a record key | 4 096 characters |
| Nesting depth below the field | 6 |

Each instance of a plugin has its own fields, so every poll in a deck gets its own 50 000 votes. Once a field is full, the relay refuses writes that would add another entry, while changing or removing an existing entry still works. The presenter's own writes are never limited. The relay also stops taking audience writes while it is short of memory, and takes them again once it has room.

### When a write is refused

A refused write does not leave the viewer looking at something the presenter never got. The relay tells that viewer's page, which replaces its copy of the shared state with the relay's: a refused vote shows as not cast (or as the vote they had before), a refused question disappears from their list. The viewer's plugin gets a `refusal` prop, `{ reason, at }`, and shows a short message:

| `reason` | Why | Message in the built-in plugins |
| --- | --- | --- |
| `full` | the field is at its limit above | "Your vote didn't reach the presenter: the session is full." |
| `busy` | the relay is short of memory | "Your vote didn't reach the presenter. The live server is busy, try again in a moment." |
| `invalid` | the write was outside `audienceWrites` or out of bounds (a plugin bug) | "Your vote didn't reach the presenter." |

The prop stays set until the viewer writes to the same plugin instance again. The built-in Q&A also puts a refused question back into the ask box, unless the viewer has started typing a new one. Your own plugin can do the same with `RefusalNote` and `refusalMessage` from `@liebstoeckel/plugin-ui`:

```tsx
import { RefusalNote } from "@liebstoeckel/plugin-ui";

function ApplauseSlide(p: ClientProps<ApplauseState>) {
  return (
    <Card>
      {/* ... */}
      <RefusalNote refusal={p.refusal} what="applause" />
    </Card>
  );
}
```

Because the page replaces the shared state, the `doc` a plugin gets can change during a session. Read it from the props on each render and don't keep it anywhere else; `state` and `snapshot` follow the new one by themselves.

While audience writes are refused because a field is full or the relay is busy, the presenter view shows a banner saying so. It goes away once audience writes arrive again. The banner is on the presenter's own screen only, never on the projected deck.

Pages built before this change keep working with a current relay, but they are not told about refused writes.

To make these limits work for your plugin, key a field that grows with the audience by participant (one entry per viewer, overwritten when they change their mind), keep per-viewer values to single values where you can, and prune entries that stop mattering, as the reactions plugin does. Also count derived values, such as upvotes per question, in one pass over the record: a pass per item gets slow on a phone once a session has thousands of entries.
