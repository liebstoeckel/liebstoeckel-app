## Why liebstoeckel

liebstoeckel is a code-first presentation framework built around the live room: decks are MDX and TSX, a live session gives every phone one shared state, and any interaction is a plugin. The same deck builds to one HTML file that presents offline and turns back into a project.

<dl class="home-ledger">
  <div class="lrow">
    <dt>One state for the whole room</dt>
    <dd>Run a deck live and the room joins by QR, no app and no account. Every phone shares one Yjs state with your screen: polls, audience Q&A and reactions update everywhere as they happen. Unhosted, plugins render a quiet fallback.</dd>
    <a class="lrow-link" href="/guides/live/">guides/live <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>Any interaction is a plugin</dt>
    <dd><code>definePlugin</code> takes a typed schema for the shared state and React for the views. A quiz, a vote that redraws a diagram, a game the room plays: write it yourself or have your agent write it.</dd>
    <a class="lrow-link" href="/plugins/building-a-plugin/">plugins/building-a-plugin <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>Written as source, with any agent</dt>
    <dd><code>liebstoeckel skill install --global</code> teaches your coding agent (Claude Code, Codex, Cursor, Gemini) the same CLI you use and the plugin SDK: it reads the component registry, writes MDX and TSX you own, and loops on <code>build --check</code> until the deck is green.</dd>
    <a class="lrow-link" href="/reference/cli/">reference/cli <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>One file, still editable</dt>
    <dd>Every deck builds to one portable <code>.html</code>: JS and CSS inlined, assets base64'd. No server, no CDN. It drops into an email, a USB stick, an air-gapped room. And it isn't a dead end: <code>liebstoeckel eject</code> turns a built file back into an editable project.</dd>
    <a class="lrow-link" href="/guides/building/">guides/building <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>Motion that matters</dt>
    <dd>Magic Move (<code>layoutId</code>), spring choreography, animated code diffs: the reason to build our own engine instead of bending a generic tool.</dd>
    <a class="lrow-link" href="/guides/animated-code/">guides/animated-code <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>Brands, not styles</dt>
    <dd>A deck declares <code>brand: "acme"</code> and inherits the whole look from typed design tokens. Override one token for a one-off without forking the theme.</dd>
    <a class="lrow-link" href="/guides/theming/">guides/theming <span aria-hidden="true">&rarr;</span></a>
  </div>
  <div class="lrow">
    <dt>Mobile-ready</dt>
    <dd>The audience joins from a phone. Tap a glowing plugin to interact full-size, swipe to navigate, and the presenter view adapts down to a handset.</dd>
    <a class="lrow-link" href="/guides/mobile/">guides/mobile <span aria-hidden="true">&rarr;</span></a>
  </div>
</dl>

## The 30-second tour

```bash frame="none"
bun add -g @liebstoeckel/cli       # or: bunx @liebstoeckel/cli …
liebstoeckel new my-talk           # scaffold a deck
liebstoeckel live my-talk          # present live (audience joins by QR)
liebstoeckel build my-talk         # → one self-contained dist/my-talk.html
```
