One binary, `liebstoeckel`, with subcommands. A bare path is shorthand for `live`.

```bash
liebstoeckel <command> [args]
liebstoeckel <deck>            # shorthand for: liebstoeckel live <deck>
liebstoeckel --help            # the command surface
liebstoeckel <command> --help  # arguments and options for one command
liebstoeckel --version
```

Every command has its own `--help` listing its arguments, options, and defaults.
The short alias `lst` is interchangeable with `liebstoeckel` (e.g. `lst build`).

## Machine output (`--json`)

Commands that list something, report a status, or return a result you act on have a
**JSON mode**, so a script or an AI agent never has to parse prose. The same rules hold
for every one of them.

- **When.** JSON mode is on with `--json`, and by default whenever stdout is not a
  terminal (piped, redirected, run by an agent or in CI). Pass `--no-json` to get the
  human output in a pipe. `dev` is the exception: it is a server, and prints its startup
  line as JSON only with an explicit `--json`. `dev poll` always prints JSON.
- **One document.** In JSON mode stdout carries exactly one JSON document, whether the
  command succeeds or fails. Progress lines, warnings and the output of tools the command
  runs go to stderr.
- **Errors.** A failure is one object with a stable `code` to branch on, a readable
  `error`, and often a `hint` with the next step:

  ```json
  { "ok": false, "error": "not logged in", "code": "not_logged_in", "hint": "…" }
  ```

  A failure that is also a result keeps its result shape with `"ok": false`: a failing
  `build --check` still lists its `diagnostics`, and a `pull` with conflicts lists them.
- **Exit codes.** `0` success, `1` failure, `2` usage error (an unknown option, a
  missing or invalid argument).
- **Unknown options are refused** on every command, before it does anything, with exit
  code `2` and the closest option it does take:

  ```text
  ✕ unknown option --josn for `liebstoeckel decks`
    did you mean --json? (see `liebstoeckel decks --help`)
  ```

| Command | JSON mode |
| --- | --- |
| `add`, `registry list`/`view`, `build`, `pack`, `licenses`, `doctor` | yes |
| `push`, `pull`, `sync status`/`commit`, `orgs` (`orgs list`), `decks` (`list`/`move`/`delete`), `folders` (`list`/`create`/`rename`/`delete`), `brand list` | yes |
| `dev` | startup line with `--json` |
| `dev poll` | always |
| `new`, `eject`, `skill`, `thumbs`, `export`, `orgs use`, `brand push`/`pull` | no: they write files or change a setting and print what they did |
| `live`, `relay`, `login`, `update` | no: servers, an interactive sign-in, and `bun`'s own output |

### Error codes

| `code` | From | Meaning, and what to do |
| --- | --- | --- |
| `unknown_option` | any command | an option the command does not take (exit 2); the hint names the closest one |
| `usage` | any command | a missing or invalid argument (exit 2); the hint shows the usage |
| `not_found` | `registry view`, `push`, `licenses`, cloud commands | the item, file or org does not exist |
| `not_a_deck` | `pack`, `dev` | the folder has no `index.html`; pass `--dir <deck>` |
| `untrusted_deck` | `build`, `licenses` | the deck has not been trusted on this machine. Building runs its code, so a human decides; an agent should ask, not approve it on its own |
| `build_failed` | `build` | the build threw; `error` has the message |
| `no_notices` | `licenses` | the built `.html` carries no license notices; run it on the deck source instead |
| `add_failed`, `pack_failed`, `install_failed` | `add`, `pack`, `doctor --install-chromium` | the step failed; `error` has the message |
| `not_logged_in` | cloud commands | no credentials; liebstoeckel cloud is coming soon |
| `session_expired` | cloud commands | run `liebstoeckel login` again |
| `forbidden` | cloud commands | your role or plan does not allow this; `error` says which |
| `terms_not_accepted` | cloud commands that create or change something | the account has not accepted the terms of service; `url` is the dashboard, where a person signs in and accepts. An agent should show the link, not accept on the user's behalf |
| `not_linked` | `pull`, `sync` | the folder is not linked to a cloud deck; `push --source` first |
| `confirmation_required` | `decks delete` | deleting needs a yes (exit 2); pass `--yes` when no one can answer the prompt |
| `folder_not_found` | `decks move`, `folders` | no folder at that path; the hint names the `folders create` command |
| `folder_exists` | `folders rename`, `folders delete` | a sibling already has that name (names are unique regardless of case) |
| `folder_not_empty` | `folders delete` | the folder still holds decks or folders; only an owner or admin can delete it, or move its content out first |
| `folder_cycle` | `folders delete` | the content cannot move into the folder being deleted |
| `invalid_name` | `folders` | a folder name is empty, over 100 characters, or holds a `/` |
| `request_failed` | cloud commands | the control plane answered with an error; `error` has the status |
| `failed` | any command | an unexpected error; `error` has the message |
| `no_dev_server`, `unauthorized`, `forbidden_host`, `poll_failed`, `invalid_reply`, `invalid_data_json`, and the dev server's reply codes | `dev poll` | see [`dev poll`](#dev-poll) |
| `port_in_use`, `live_failed` | `dev --json` | the port is taken; the live mirror could not start |

## `new`

Scaffold a new deck. It materializes in the **current directory** as `./<name>`;
pass `--dir <parent>` to put it elsewhere (e.g. `--dir presentations` to drop it
into a monorepo's workspace glob).

```bash
liebstoeckel new <name> [--brand <brand>] [--dir <parent>] [--no-org-brand]
```

| Flag | Meaning |
| --- | --- |
| `--brand <brand>` | brand theme to wire in (default: `liebstoeckel`, or your org's default brand when logged in) |
| `--dir <parent>` | parent directory for the deck (default: the current directory) |
| `--no-org-brand` | don't bake the logged-in org's default brand; use the plain `liebstoeckel` brand |

Generates `index.html`, `main.tsx`, `build.ts` (using `buildDeck` from `@liebstoeckel/thumbnails/build`), `server.ts`, `bunfig.toml`, and a starter `slides/01-intro.tsx`. The name must be lower-case letters/digits/hyphens; it won't overwrite an existing directory.

When you're **logged in** (and didn't pass `--brand`), `new` automatically bakes your
org's **default brand** into the deck as owned source: `brands/<name>.ts`, wired into
`<Present brandThemes={…}>`, with `data-brand` set, so new decks are on-brand
instantly (see [`brand`](#brand)). Pass `--no-org-brand` to opt out, or `--brand` to
choose a specific one. It's best-effort: offline or signed-out, you just get the
default `liebstoeckel` brand.

## `add`

Scaffold registry items (charts, hooks, layouts, …) into a deck as **owned
source**: the code is copied into your project, not imported from a package, so
you can edit it freely. Leaf dependencies the items need (e.g. the relevant
`@visx/*` packages) are installed into the deck.

```bash
liebstoeckel add bar-chart                       # one item into the current deck
liebstoeckel add chart bar-chart line-chart      # several at once (optional category word)
liebstoeckel add donut-chart --dir ./presentations/demo
liebstoeckel add bar-chart --dry                 # show the plan, write nothing
```

| Flag | Meaning |
| --- | --- |
| `--dir <deck>` | target deck directory (default: current directory) |
| `--dry` | print the plan (files + dependencies) without writing |
| `--force` | overwrite files that already exist (default: skip them) |
| `--no-install` | don't run `bun add` for the items' dependencies |
| `--json` | structured plan/result output (default when stdout isn't a TTY) |

`add` always **prints its plan before writing**: which files it will create,
overwrite, or skip, plus the dependencies it will install. Files land under the
deck's `charts/` (or the item's own path); existing files are skipped unless
`--force` (so re-running is idempotent). Dependencies are installed with
`bun add --ignore-scripts` (the registry trust model), or skipped with
`--no-install` so you can run it yourself. With `--json` (or when piped), the plan
(`--dry`) or the result emits as JSON for an agent to consume.

Items resolve through a registry **namespace**. A bare name (`bar-chart`) comes
from the bundled default registry (`@liebstoeckel`); a scoped ref (`@acme/heatmap`)
comes from a registry you map in the deck's `liebstoeckel.json` under
`"registries"`, which today accepts a `"default"` keyword or a local path, with
npm/git/HTTP transports planned. Categories are `chart`, `hook`, `element`,
`component`, `layout`, `motion`; the leading category word is optional sugar.

## `registry`

Browse the chart/component registry: the discovery surface for [`add`](#add), and the
machine-readable contract agents read before scaffolding.

```bash
liebstoeckel registry list                 # the catalog (name · type · data shape)
liebstoeckel registry view bar-chart       # one item: exports, props, dataShape, example
liebstoeckel registry list --json          # JSON (default when piped / not a TTY)
```

`view` returns each component's **`dataShape`**, the exact type of its `data` prop,
so you (or an agent) can wire data without reading the source. Output is JSON when
`--json` is passed or stdout isn't a TTY, and a compact human view otherwise. This
reads the bundled `@liebstoeckel` registry.

## `build`

Build a deck to a single self-contained `.html` (+ thumbnails), written to
`./dist/<deck-slug>.html`. The slug is the deck folder name, e.g. `poll-demo/` →
`dist/poll-demo.html`. By default the build also
embeds a compressed copy of the deck's **own source** (slides, `package.json`, etc., not
`node_modules`), so the compiled `.html` can later be [`eject`](#eject)ed back to an editable
project. Source collection uses `bun pm pack`, so your deck's `package.json` `"files"` list
controls exactly what's embedded.

The deck defaults to the **current directory**; pass it as a positional `[dir]` or
with `--dir <deck>` (the convention shared by `pack`/`live`/`export`).

The build also embeds a **third-party license notice** built from the modules that
actually end up in the bundle (React, Motion, Yjs, the fonts, and the MPL-2.0 engine).
Minification strips license comments, so this puts the required attribution back. It is
recomputed on every build, so it stays correct when you swap a font or a library. Read
it with [`licenses`](#licenses).

The build requires a **single copy of each `@liebstoeckel/*` package**. A deck compiles
into one file, so if two framework packages disagree on a version — for example after
bumping `@liebstoeckel/engine` but leaving a plugin on an older release — the bundle would
embed two incompatible copies side by side. The build stops, prints the conflicting
versions, and asks you to update the framework packages together (e.g. `bun update`) so
they resolve to one version. `--check` reports the same conflict without writing anything.

```bash
liebstoeckel build                             # the deck in the current directory
liebstoeckel build --dir <deck>                # or a positional [dir]
liebstoeckel build [dir] --no-inline-package   # build WITHOUT the recoverable source
liebstoeckel build [dir] --check               # validate only: no artifact, structured errors
liebstoeckel build [dir] --check --visual      # + render each slide and lint for cut-off text
liebstoeckel build [dir] --trust               # pre-approve an unfamiliar deck's build-time code
LIEBSTOECKEL_NO_THUMBS=1 liebstoeckel build [dir]   # skip thumbnails
```

<Aside type="danger" title="Building a deck runs its code">
A deck is **code**. Building it runs the deck's build-time modules (Bun macros such as the
animated-code macro, and build plugins) in this process with full access to your files and
network — so building a deck you did not write is arbitrary code execution on your machine.
The first time you build an unfamiliar deck, `build` asks you to confirm trust and remembers
your answer. Decks you scaffold with [`new`](#new) are trusted automatically. In a
non-interactive shell (CI) it refuses unless you pass `--trust` or set
`LIEBSTOECKEL_TRUST_BUILD=1`. **Only build decks you trust.** (Note: `--ignore-scripts`
blocks npm lifecycle scripts, not a deck's macros — it is not a substitute for this.)
</Aside>

Thumbnails need a headless Chromium; the build skips them (never fails) when none is
found. See [Chromium setup](/guides/chromium/) to install one or point at an existing
binary with `LIEBSTOECKEL_CHROMIUM`.

| Flag | Meaning |
| --- | --- |
| `--no-inline-package` | don't embed the deck's source (smaller file, not ejectable) |
| `--no-inline-licenses` | don't embed the third-party license notices (not recommended) |
| `--allow-secret` | override the secret gate that aborts if a packed file looks like a credential |
| `--check` | validate the deck **bundles** and resolves one copy of each framework package (no output written); reports diagnostics + exits non-zero on error |
| `--visual` | with `--check`: also render every slide headless and lint for cut-off or overflowing text (needs Chromium; skips with a reason when none is found) |
| `--trust` | pre-approve this deck's build-time code (a deck is code; remembered after the first build) |
| `--json` | machine-readable JSON result (default when stdout isn't a TTY); progress goes to stderr |

`--check` is the fast validation gate (no Chromium, no thumbnails, nothing written):
it returns `{ ok, diagnostics }`, each diagnostic carrying `message`/`file`/`line`,
and exits non-zero when the deck doesn't bundle. It checks that imports resolve and
MDX/TSX transforms; it does not type-check. Output is JSON when piped or with `--json`.

`--check --visual` adds a rendered lint pass on top: it bundles a throwaway copy of the
deck, steps through every slide in headless Chromium at the native 1280x720 stage, and
flags text the audience would not see: content clipped by its container
(`clipped-text`), chart labels sticking past their svg viewport (`svg-clipped-text`),
and text extending beyond the stage (`offstage-text`). Findings land under `visual` in
the JSON result, each with the slide index, a text snippet, a DOM path, and the overflow
in pixels; any finding makes `ok` false and the exit code non-zero, so an agent can loop
on it like a build error. Like thumbnails, it needs a headless Chromium; without one the
pass is skipped with a reason (`visual.skipped`) and does not fail the check.

With `--json` (or piped), a normal **write** build prints the human progress to stderr and
emits a single result object on stdout, so an agent can read the artifact path without
scraping prose:

```json
{ "ok": true, "artifact": "/abs/path/dist/my-talk.html", "outfile": "my-talk.html", "thumbnails": 6 }
```

`thumbnails` is `null` (with a `thumbnailsSkipped` reason) when no Chromium is available.
A refused untrusted build emits `{ "ok": false, "error": "untrusted deck", "code": "untrusted_deck", "hint": "…" }`
and exits non-zero. Trusting a deck you didn't write means agreeing to run its build-time
code on your machine — a human decision; an AI agent should surface it rather than approve
on its own. A human who trusts the deck approves it with `--trust` (or `LIEBSTOECKEL_TRUST_BUILD=1`).

<Aside type="caution" title="Anyone with the file has the source">
The embedded source is recoverable by anyone with the `.html`. A `"files"` allowlist in the deck's
`package.json` (the scaffold ships one) keeps secrets out by construction; the build also refuses to
embed a `.env` or a file matching a credential signature. Use `--no-inline-package` to ship an opaque deck.
</Aside>

## `eject`

Recover a built deck's editable source from its `.html`.

```bash
liebstoeckel eject <deck.html> [outdir] [--force]
```

`outdir` defaults to `<deck>-source/`. Eject refuses a non-empty directory unless `--force`, and
errors clearly if the HTML carries no embedded source (e.g. it was built `--no-inline-package`).
Rebuilding runs the deck's own build-time code (macros/build plugins) — `--ignore-scripts`
only blocks npm lifecycle scripts, not that — so **only rebuild a deck you trust**.
`liebstoeckel build` confirms an unfamiliar deck once (see the warning under [`build`](#build)):

```bash
cd <outdir> && bun install --ignore-scripts && liebstoeckel build
```

For the full recover → edit (by hand or with an agent) → rebuild loop, see
[Editing a built deck](/guides/editing-a-built-deck/).

## `pack`

Inspect, or emit, exactly the source a build would embed, without running a full build.
The deck defaults to the **current directory**; pass it as `[dir]` or `--dir <deck>`.

```bash
liebstoeckel pack [dir]                  # print the file list (defaults to cwd)
liebstoeckel pack [dir] -o deck.tgz      # write a gzip tarball (bun add-compatible)
liebstoeckel pack [dir] --allow-secret   # override the secret gate
liebstoeckel pack [dir] --json           # { dir, files, out } (default when piped)
```

With `--json` (or piped) the result is `{ "dir": "/abs/deck", "files": ["index.html", …], "out": null }`,
where `out` is the absolute path of the `-o` tarball when one was written.

## `licenses`

Report the third-party licenses bundled into a deck. Pass a built `.html` to print
the notices it already carries, or a deck `[dir]` / `--dir <deck>` (default: cwd) to
compute the report fresh from the deck's real module graph.

```bash
liebstoeckel licenses dist/my-deck.html   # print the notices embedded in a built deck
liebstoeckel licenses                     # compute the report for the deck in cwd
liebstoeckel licenses --dir <deck>        # or a positional [dir]
liebstoeckel licenses [dir] --json        # structured: { ok, packages, firstParty, flagged }
liebstoeckel licenses [dir] --check       # exit non-zero if any non-standard license is bundled
```

The report lists only what is actually inlined into the `.html`: the client bundle and
the embedded fonts. Build-time tools like the MDX compiler, Tailwind, and the syntax
highlighter run during the build and aren't redistributed, so they're left out.

A built **`.html`** carries its notices as rendered text, so the command prints them
(with `--json`, as `{ source, notices }`). A deck **directory** is recomputed from a
fresh bundle, so it gives the full structured report (`{ ok, packages, firstParty,
flagged }`) and is the only input that works with `--check`. As with `build --check`,
the output is JSON when piped or with `--json`.

`--check` is a CI gate: it fails when a bundled package carries a license outside the
permissive/embeddable set (for example a copyleft chart library pulled in via
[`add`](#add)), so you catch it before shipping.

<Aside type="note" title="Notices are embedded automatically">
Every `build` embeds these notices into the `.html` (see [`build`](#build)); `licenses`
is for inspecting and gating them. Disable the embed with `build --no-inline-licenses`
only if you have another way to satisfy the attribution requirements.
</Aside>

Useful for verifying your `"files"` allowlist before shipping. The `-o` tarball is standard gzip
(`bun add ./deck.tgz`-installable); the in-HTML embed uses zstd internally.

## `dev`

Serve a deck for authoring: hot reload plus the dev shell (a sidebar beside
the deck; the plain deck alone is behind `/deck`), whose first tool is [live annotations](/guides/dev-mode/) an AI agent can apply to
your slide source while you watch. With `--dir`, the server re-executes with
the deck as its working directory so the deck's own `bunfig.toml` plugins load;
a port already in use fails with a message naming it. A `[serve.static]` plugin
that cannot be found from the deck folder is reported before the URL (and in
the `--json` startup line as `pluginProblems: [{ plugin, message }]`); the
server keeps running and shows an error page in place of the deck until
`bun install` in the deck folder makes it resolve.

```bash
liebstoeckel dev                     # the deck in the current directory
liebstoeckel dev --dir <deck> --port 3000
liebstoeckel dev --host 0.0.0.0      # expose beyond localhost (trusted networks only)
liebstoeckel dev poll                # agent side: wait for an annotation batch
liebstoeckel dev poll --reply <batchId> done --data '{"applied":["<id>"],"files":["slides/01-title.mdx"],"notes":[]}'
```

| Flag | Meaning |
| --- | --- |
| `--dir <deck>` | deck directory (default: current directory) |
| `--port N` | port (default: 3000) |
| `--host <addr>` | bind hostname (default `127.0.0.1`) |
| `--json` | machine-readable startup info: `{ ok, url, port, pluginProblems? }`, or the error object (`not_a_deck`, `port_in_use`, …) |

### `dev poll`

`dev poll` is the agent side. It blocks until the browser sends work (up to
`--timeout` ms, default 600000), prints one JSON event, and exits; every event
carries an `_instructions` field telling the agent exactly what to do next.
Replies are `done` with a JSON result or `error "reason"`.

| Event `type` | What it is | Reply |
| --- | --- | --- |
| `apply` | a batch of annotations and slide requests the user sent | once, `done` or `error` |
| `deck_log` | a warning or error the open deck logged: `level` (`warn` or `error`) and `message` | none |
| `plugin_status` | the deck's bundler plugins: `ok`, `problems` (`{plugin, message}`), and `fix` while some do not resolve | none |
| `timeout` | nothing arrived within `--timeout` | none |
| `exit` | the dev server stopped; stop polling | none |

After any event, poll again (except after `exit`). An `apply` stays claimed by you
until you reply; the other events are delivered once and never hold anything up.

| Flag | Meaning |
| --- | --- |
| `--dir <deck>` | deck directory (default: current directory); the running server is found through its `.liebstoeckel/dev/server.json` |
| `--timeout <ms>` | how long to wait for an event before printing a `timeout` event and exiting (default 600000) |
| `--reply <id>` | reply to the event with this id instead of waiting; pair with a positional `done` or `error "reason"` |
| `--data <json>` | the JSON result for a `done` reply: `{"applied": [annotationIds], "files": [paths], "notes": [strings]}` |

Every failure is one JSON object on stdout, `{ "ok": false, "error", "code", "hint"? }`:
`no_dev_server` when no dev server runs for the deck (or its record is stale),
`unauthorized` when the server restarted with a new token, `forbidden_host` when it
rejected the `Host` header, `poll_failed` for anything else, and `invalid_reply` /
`invalid_data_json` (exit 2) for a malformed `--reply` command line. A refused reply
carries the dev server's own code, e.g. `batch_already_resolved` for a second reply to
the same batch (safe to treat as done), `unknown_reply_id` or `applied_id_not_in_batch`.

The first run adds a small inert loader tag to the deck's `index.html`. It
only activates under `dev`, where it loads the bridge script that connects the
framed deck to the sidebar, and every `build` strips it, so built decks are
unaffected.
Dev-mode state (annotations, screenshots, revert snapshots) lives under
`.liebstoeckel/dev/` in the deck and is git-ignored.

If `liebstoeckel dev` reports that it could not load `@liebstoeckel/dev-server`,
the message names the underlying error; set `LIEBSTOECKEL_DEBUG=1` to also
print its stack trace.

## `live`

Present a deck to a room. Builds the deck if given a project dir, and captures
slide thumbnails by default (so the overview grid is instant); the capture is
skipped, not failed, when no Chromium is available.

The deck defaults to the **current directory**; pass it as a positional or with
`--dir <deck>` (the same convention as `build`/`pack`/`export`).

```bash
liebstoeckel live                               # the deck in the current directory
liebstoeckel live <deck.html | deck-dir> [--port N]
liebstoeckel live --dir <deck> --relay <url> --relay-token <token>
liebstoeckel live <deck> --no-thumbnails        # skip the capture step
```

| Flag | Meaning |
| --- | --- |
| `--port N` | LAN port (default: auto) |
| `--relay <url>` | present through a [relay](/guides/relay/) instead of LAN |
| `--relay-token <tok>` | relay account token (or `LIEBSTOECKEL_RELAY_TOKEN`) |
| `--no-thumbnails` | skip thumbnail capture (also via `LIEBSTOECKEL_NO_THUMBS=1`) |
| `--format` / `--width` / `--quality` / `--scale` | tune thumbnails, as in [`thumbs`](#thumbs) |

## `relay`

Run a public relay server.

```bash
liebstoeckel relay [--port N] [--tokens tok1,tok2] [--public-url https://…]
```

| Flag | Meaning |
| --- | --- |
| `--port N` | listen port (or `PORT`) |
| `--tokens` | comma-separated account tokens (or `PRESENT_RELAY_TOKENS`); one is generated if omitted |
| `--public-url` | the public `https://` origin (so links/WebSocket use `wss://`) |

## `thumbs`

(Re)generate thumbnails for a built deck.

```bash
liebstoeckel thumbs <built-deck.html> [--format webp|jpeg|png] [--width 640] [--quality 80] [--scale 2]
```

Needs Chromium and fails if none is found ([Chromium setup](/guides/chromium/)).

## `export`

Export slides to **PNG** files or a single **PDF** (one slide, a range, or the
whole deck), rendered headless on the native 1280×720 canvas, the same pipeline as
thumbnails. The input is a built `.html` **or** a deck source directory (built on
demand); it defaults to the **current directory**, or pass it as a positional or
with `--dir <deck>`.

```bash
liebstoeckel export [deck.html|deck-dir|--dir <deck>] [opts]
```

| flag | meaning |
| --- | --- |
| `--format png\|pdf` | output format (default: inferred from `-o`'s extension, else `png`) |
| `--slides <spec>` | 1-based, inclusive: `3`, `2-5`, `1,3,5-7`, `3-`, `-4` (default: all) |
| `-o`, `--out <path>` | PDF: the `.pdf` file. PNG: an output directory |
| `--width <n>` | viewport / page width (default `1280`, the authoring canvas) |
| `--scale <n>` | device-scale factor for PNG / raster PDF (default `2` → 2560×1440) |
| `--raster` | PDF only: image-per-page instead of the default vector PDF |
| `--quality <n>` | JPEG quality for the raster PDF (default `92`) |
| `--page-size <size>` | PDF only: the paper. `slide` (default, the page *is* the 16:9 canvas), `a3`, `a4`, `a5`, `letter`, `legal`, or an explicit `<w>x<h>` with a unit (`210x297mm`, `8.5x11in`) |
| `--orientation landscape\|portrait` | PDF only, with a paper page: default `landscape` |
| `--margin <n><mm\|cm\|in\|px>` | PDF only, with a paper page: clearance on every side (default `10mm`) |

```bash
# slide 3 of a built deck → PNG
liebstoeckel export ./dist/my-deck.html --slides 3 -o ./out

# whole deck as a PDF, building the source dir on demand
liebstoeckel export ./presentations/demo --format pdf -o demo.pdf

# printable handout: one slide per A4 page (landscape), 10 mm margin
liebstoeckel export ./presentations/demo --page-size a4 -o handout.pdf
```

**PDF is vector by default**: selectable, searchable text with embedded fonts and
vector charts/gradients, produced in a single `page.pdf()` over a print view that
stacks one slide per page (no merge, no extra dependency). Pass `--raster` for an
image-per-page PDF instead: no text layer, but pixel-exact fidelity for a slide
whose effects don't reproduce under print.

**Printing.** By default each PDF page is exactly the 16:9 slide canvas, which
prints poorly on paper. Pass `--page-size a4` (or `letter`, `a3`, an explicit
`210x297mm`, ...) to get physical pages instead: the slide is scaled to fit the
printable area (the page minus `--margin`), centered, on white paper, aspect
preserved. Landscape is the default since slides are landscape; `--orientation
portrait` fills the width and leaves the lower part of the page empty. Vector
text stays selectable, and `--raster` produces the same page geometry. A paper
page sizes the slide itself, so it cannot be combined with `--width`.

PNGs come straight off the page (lossless, native resolution), named
`<deck>-slide-NN.png` (1-based, zero-padded). Like `thumbs`, `export` needs Chromium
and fails loudly if none is found ([Chromium setup](/guides/chromium/)).

## `skill`

Install the **`liebstoeckel-deck` agent skill** into a project so AI coding agents can
create and edit decks for you (scaffold → add charts → wire data → build). The skill
ships inside the CLI package, version-pinned so it always matches your installed
`liebstoeckel`, and is placed where each agent looks for it.

```bash
liebstoeckel skill install --dir ./my-deck        # into one deck/project (writes AGENTS.md too)
liebstoeckel skill install --global               # into your user account (~) — every project
liebstoeckel skill install --target codex --dir ./my-deck
liebstoeckel skill update                         # refresh the installed skill to the CLI's version
```

| Flag | Meaning |
| --- | --- |
| `--scope <project\|user>` | where to install, a project/deck, or your user account (`~`); `--global` is shorthand for `--scope user` |
| `--target <list>` | (install) `claude`, `codex`, `cursor`, `gemini`, or `all` (default); comma-separated |
| `--dir <deck>` | the deck/project for a `project`-scope install (default: current directory) |

**Scope.** A `project` install writes the per-agent skill folders **and** the `AGENTS.md` fallback into the deck. A `user` install writes the folders under your home (`~/.claude/skills/…` and the rest) so every project sees the skill, and does **not** drop a bare `~/AGENTS.md`. When you don't pass a scope, an interactive terminal asks which you want; with `--dir` it's a project install; and a non-interactive run refuses rather than scatter skill files into a directory that isn't a deck — pass `--scope user` or `--dir <deck>` to be explicit.

It writes the same skill to each agent's path (`.claude/skills/`, `.agents/skills/` for
Codex/Gemini, `.cursor/skills/` + a rule) and merges a managed block into `AGENTS.md`,
the universal fallback for agents without skill support. Re-running is idempotent. See
the [Scaffolding guide](/guides/scaffolding/) for how an agent uses it.

The installed skill is **version-pinned to the CLI** that wrote it. `skill update`
rewrites the skill for the agent paths already present in the deck (plus the
`AGENTS.md` block) without adding new ones. You rarely need to run it yourself: the
installed skill is a pure function of the CLI version, so whenever an installed copy
is older than the CLI you run, any command refreshes it in place and prints a
one-line note on stderr. This covers project installs and a `user`-scope install
under `~` alike.

## `update`

Bring everything current in one command: the deck's `@liebstoeckel/*` packages, a
global CLI install, and every installed copy of the agent skill, whichever of those
apply.

```bash
liebstoeckel update                # the deck in the current directory (and/or the global CLI)
liebstoeckel update --dir <deck>   # a specific deck
```

| Flag | Meaning |
| --- | --- |
| `--dir <deck>` | the deck to update (default: current directory) |

What it does, in order:

1. **Checks the registry live** for the latest `@liebstoeckel/cli` (this command
   never uses the reminder cache; it also refreshes that cache with the answer).
2. **Deck-local install:** runs `bun update --latest` for exactly the
   `@liebstoeckel/*` packages the deck declares, never your other dependencies.
   Updating the whole scope together keeps the framework packages on one version,
   which the build requires.
3. **The CLI's own install root**, when the running CLI lives in a different
   project than the deck (for example a project root holding `@liebstoeckel/cli`
   with decks in subdirectories): that root's declared `@liebstoeckel/*`
   packages update too, so the CLI itself never stays behind. A CLI install the
   command cannot manage (not declared where it is installed) is called out
   explicitly instead of being skipped in silence.
4. **Global install** (the CLI was installed with `bun add -g`): runs
   `bun add -g @liebstoeckel/cli@latest`. Shapes combine when several apply.
5. **Refreshes the agent skill** wherever it is installed (the deck and your user
   account), using the freshly installed CLI, so the skill version matches the new
   CLI.

Outside a deck and without a global install there is nothing to act on, and the
command says so instead of guessing.

After a deck update the command verifies that every `@liebstoeckel/*` package
resolved to a single version. Releases bump dependents together, so a split is
rare, but a package published against an older sibling can keep a stale nested
copy that targeted updates never re-resolve; when that happens the command
prints the affected packages and the clean reinstall
(`rm -rf node_modules bun.lock && bun install`) that collapses them.

## `doctor`

Check the build environment — the Bun version (must satisfy the CLI's `engines.bun`) and whether a Chrome/Chromium was found for thumbnails and PNG/PDF export. Optionally install one.

```bash
liebstoeckel doctor                     # human summary (Bun + Chromium + config path)
liebstoeckel doctor --json              # machine-readable (default when piped)
liebstoeckel doctor --install-chromium  # download Playwright's Chromium, record its path
```

| Flag | Meaning |
| --- | --- |
| `--install-chromium` | Install Playwright's Chromium if none resolves, then record its path in `~/.config/liebstoeckel/config.json` so every later build/export reuses it |
| `--json` | Machine-readable output (default when piped) |
| `--dir <deck>` | Deck to check for scaffold migrations and bundler plugins (default: the current directory) |

`doctor` resolves Chromium the same way builds do (see [Chromium setup](/guides/chromium/#resolution-order)): an existing system Chrome is found automatically, so often nothing needs installing. Only `export`/`thumbs` require a browser; `build` skips thumbnails without one. When no browser is found, the human output lists every probed location, and `--json` adds them as `probedCandidates`.

The report also includes CLI staleness from the cached registry check (never a live
lookup, so `doctor` stays network-free): `--json` carries
`cli: { version, latestKnown, updateAvailable }`. Agents can gate on
`updateAvailable` and suggest [`liebstoeckel update`](#update); `latestKnown` is
`null` when no check has completed yet (for example offline).

### Bundler plugins

Inside a deck (or with `--dir <deck>`), `doctor` also resolves the bundler
plugins listed under `[serve.static] plugins` in the deck's `bunfig.toml`
(Tailwind, MDX), the same check `liebstoeckel dev` runs at startup. Each plugin
that cannot be found gets one line naming it, with the fix: run `bun install` in
the deck, or correct the plugin list. `--json` carries the same data as
`pluginProblems`, an array of `{ plugin, message }` that is empty when every
plugin resolves or the deck has no `bunfig.toml`. A `bunfig.toml` that is not
valid TOML shows up as one entry with `plugin: "bunfig.toml"`. An unresolved
plugin does not change the exit code, which stays non-zero only for a Bun
version that does not fit.

### Scaffold migrations

Scaffolded deck source is yours, and the conventions it starts from keep
improving. When a convention changes after a deck was created, `doctor` detects
the gap instead of leaving the deck to drift: run it inside a deck (or pass
`--dir <deck>`) and `--json` carries a `migrations` array with one entry per
known migration:

```json
"migrations": [
  {
    "id": "0001-hmr-entry-boundary",
    "needed": true,
    "since": "0.3.11",
    "reference": "references/migrations/0001-hmr-entry-boundary.md",
    "reason": "slide edits in dev mode reset the deck to slide 1 ...",
    "autoPatchable": true
  }
]
```

`needed` says the deck predates the convention; `reference` names the guide
(shipped inside the installed agent skill) with the why and the manual edit;
`autoPatchable` says [`liebstoeckel dev`](#dev) would apply it automatically.
`doctor` itself never modifies anything.

When `dev` starts, it applies every needed migration whose file still matches
the scaffolded shape, printing one notice per patched file
(`↻ migrated main.tsx (0001-hmr-entry-boundary): <reason>`); the patch always
includes a comment explaining itself. A file that diverged from the scaffold
is never rewritten, only hinted about.

A deck that deliberately diverges can opt out per migration in its
`package.json`, with a mandatory reason:

```json
"liebstoeckel": {
  "migrationOptOut": {
    "0001-hmr-entry-boundary": "custom HMR via our own dispose handler"
  }
}
```

A suppressed migration is never detected, hinted, or patched; `doctor --json`
still lists it with `suppressed: true` and the reason, and warns (as
`migrationWarnings`) about opt-out entries that suppress nothing (an empty
reason, or an unknown id).

## Staying up to date

The CLI checks its registry for a newer `@liebstoeckel/cli` at most **once an hour**,
in a detached background process, and prints a one-line note on a later run when an
update exists. The check shells out to `bun pm view`, so it follows the same registry
configuration as your installs (a scoped registry in `.npmrc`/`bunfig.toml`, or the
public npm registry); no command ever waits on the network for it. Acting on the note
is one command:

```bash
liebstoeckel update   # CLI + the deck's @liebstoeckel/* packages + the agent skill
```

Reminders appear only on an interactive terminal. They are suppressed with `--json`,
when output is piped (agents), when `CI` is set, and entirely with
`LIEBSTOECKEL_NO_UPDATE_CHECK=1`. The check interval can be tuned with
`LIEBSTOECKEL_UPDATE_CHECK_INTERVAL=<seconds>`. The agent-skill refresh is separate
from these reminders: a stale installed skill is refreshed automatically on any
command, in every mode (see [`skill`](#skill)).

### `login`

Sign in to **liebstoeckel cloud** (the hosted control plane) from the terminal using the
OAuth 2.0 device-authorization grant (RFC 8628), with no password. The CLI prints a URL;
open it in a browser, sign in with an email one-time code, and approve. The resulting
token is stored in `~/.config/liebstoeckel/credentials.json` (mode `600`).

```bash
liebstoeckel login --api https://<your-control-plane-host>
```

| Flag | Meaning |
| --- | --- |
| `--api <url>` | the control-plane base URL (or set `LIEBSTOECKEL_API`) |

### `push`

Upload a built single-file deck to your cloud dashboard. Authenticates with the token
from `login`; the deck appears in your dashboard's deck list, and for a **team org** it's
visible to every member (the shared library).

```bash
liebstoeckel build                       # produces ./dist/<deck-slug>.html
liebstoeckel push                        # no path → that built deck in ./dist
liebstoeckel push --org acme             # push into a team you belong to
liebstoeckel push ./dist/my-deck.html --title "My deck"   # explicit path + title override
liebstoeckel push --folder "Sales/Q4"    # a new deck goes into that folder
```

**Re-push = a new version.** `push` identifies a deck by a stable **key** (the deck
folder name, or `--name <key>`); pushing the same key again updates that deck **in place
at the same URL** (a new version on Pro; the latest is replaced on free). `--new` forces a
separate deck. With **no path**, `push` uploads the single built `.html` in `./dist`
(run `build` first). The **title** comes from `--title` → the deck's own embedded
`<title>` → the deck key: the server reads the `<title>` straight from the
uploaded file, so any Unicode (em-dashes, smart quotes, emoji) just works. Only an
explicit `--title` override travels as a header (URL-encoded). A **cover** is read from
the deck's built-in thumbnails.

| Flag | Meaning |
| --- | --- |
| `--title <title>` | override the title (default: the deck's embedded `<title>`, then its key) |
| `--name <key>` | the deck key to upsert (default: the deck folder name) |
| `--new` | create a separate deck instead of updating the matching one |
| `--folder <path>` | put a **new** deck into this folder (e.g. `"Sales/Q4"`), creating missing folders; ignored, with a note, for a deck that already exists |
| `--org <slug>` | push into this organization (default: the one set by `orgs use`, else personal) |
| `--api <url>` | override the stored control-plane host |
| `--json` | machine-readable result (default when piped); progress goes to stderr |

With `--json`:

```json
{ "ok": true, "deck": { "id": "…", "title": "My deck" }, "version": 3, "isNew": false, "key": "my-deck", "org": null, "api": "https://…", "folder": null, "folderIgnored": false }
```

`folder` is the folder a new deck was put in (`null` without `--folder`). A re-push never
moves a deck: moving is explicit (`decks move`), so a teammate's push can't undo someone
else's filing. `folderIgnored` is `true` when `--folder` was given for a deck that already
exists; the prose output then prints the `decks move` command that would move it.

With `--source` it adds `source`: `{ "ok": true, "changed": true, "commit": "…" }`, or
`{ "ok": false, "conflicts": [{ "path", "kind" }] }` (then `ok` is false and the exit code 1).

### `orgs`

List the organizations (personal workspace + teams) you belong to, and choose which one
`push` targets by default.

```bash
liebstoeckel orgs                        # list workspaces; → marks the push default
liebstoeckel orgs use acme               # make "acme" the default for push
liebstoeckel orgs --json                 # { active, orgs, default } (default when piped)
```

`orgs --json` (the same as `orgs list --json`) returns `active` (`{ slug, name, role,
personal, plan }`), `orgs` (`[{ slug, name, personal }]`) and `default`, the slug `push`
targets without `--org` (`null` = your personal workspace).

Teams, members, roles (`owner` / `admin` / `member`), and invitations are managed in the
dashboard's **Team** page; the CLI only needs to pick which org a deck lands in.

### `brand`

Share governed **brand token sets** across a team. Your org is an authenticated registry
(the same protocol as `add`/`registry`); a brand is pulled into a deck as **owned source**
(`brands/<name>.ts`) and baked at build, so the deck stays self-contained and WYSIWYG.

```bash
liebstoeckel brand list                  # brands in your org (→ marks the default)
liebstoeckel brand push ./brand.ts --default   # upload a theme token file (admins/owners)
liebstoeckel brand pull acme             # write brands/acme.ts into the current deck
liebstoeckel new my-deck                 # auto-applies the org's default brand
```

`brand push` accepts a `defineTheme(...)` module or a flat tokens JSON. Editing is also
available in the dashboard's **Brand** page. Brand sharing is a paid (Pro/Team) feature.

A brand's fonts are picked from a curated [Fontsource](https://fontsource.org) catalog in
the Brand page. `brand pull` writes the `import "@fontsource-variable/…"` into
`brands/<name>.ts` **and runs `bun add`** to install those font packages, so the webfont is
inlined into your single-file deck at build (pass `--no-install` to install them yourself).
A **Custom…** font carries no package and falls back to the system font unless you supply
its own `@font-face`.

| Flag | Meaning |
| --- | --- |
| `--default` | (push) make this the org default that `new` applies |
| `--name <key>` | (push) brand name (default: the theme's `name`, then the file name) |
| `--dir <deck>` | (pull) the deck to write `brands/<name>.ts` into (default: cwd) |
| `--no-install` | (pull) write the files but don't `bun add` the brand's font packages |
| `--org <slug>` | the organization to act on |
| `--json` | (list) `{ org, brands: [{ name, isDefault, tokens }] }` (default when piped) |

### `decks`

List, move and delete your cloud decks in an organization. `decks` alone is `decks list`.

```bash
liebstoeckel decks                       # decks in your default workspace, with key and folder
liebstoeckel decks --org acme            # decks in a team you belong to
liebstoeckel decks move pitch q3-review --to "Sales/Q4"   # by deck key or id
liebstoeckel decks move pitch --to /     # back to the root
liebstoeckel decks delete old-talk       # asks first; lists what goes
liebstoeckel decks delete old-talk draft --yes            # no prompt (agents, scripts)
```

Decks are named by their **key** (shown by `decks list`, the name `push` upserts by) or
their **id**. Folders are named by path, `/` being the root; a path matches regardless of
case. `move` does not create folders: an unknown path fails with `folder_not_found` and a
hint to run `folders create` first.

**Moves and deletes are all or nothing.** You can move or delete a deck you created; owners
and admins can move or delete any deck. If any named deck is not yours to manage, nothing
changes, and the error lists each deck that stopped it. Deleting cannot be undone: the
deck's share and preview links stop working and its live results go with it. On a terminal
`delete` asks for a yes; without one (piped, or with `--json`) it needs `--yes` and
otherwise fails with `confirmation_required` (exit 2).

| Flag | Meaning |
| --- | --- |
| `--to <path>` | (move) the target folder, `/` for the root |
| `--yes` | (delete) delete without asking |
| `--org <slug>` | the organization to act on |
| `--json` | machine-readable output (default when piped) |

With `--json`:

```jsonc
// decks list
{ "org": null, "decks": [{ "id", "key", "title", "folderId", "folder", "version", "shared", "shareSlug", "views", "uniqueViews" }] }
// decks move
{ "ok": true, "moved": 2, "folder": "Sales/Q4", "folderId": "…", "decks": ["…", "…"] }
// decks delete
{ "ok": true, "deleted": 2, "decks": ["…", "…"] }
// a refused move or delete (exit 1)
{ "ok": false, "error": "Nothing was changed: …", "code": "forbidden", "refused": [{ "id": "…", "reason": "forbidden" }], "hint": "…" }
```

`folder` is the deck's folder path, `null` for the root; `org` is the slug listed, `null`
for your personal workspace. A `refused` entry's `reason` is `forbidden` (not yours to
manage) or `not_found`.

### `folders`

Organize an organization's decks in nested folders. Folders are purely organizational:
everyone in the org still sees every deck, and who may manage a deck does not change.
`folders` alone is `folders list`.

```bash
liebstoeckel folders                     # the folder tree
liebstoeckel folders create "Sales/Q4"   # creates missing parents too; fine if it exists
liebstoeckel folders rename "Sales/Q4" "Q4 2026"
liebstoeckel folders delete "Sales/Q4"   # its decks and subfolders move up to "Sales"
liebstoeckel folders delete Sales --to /  # …or somewhere else ("/" is the root)
```

Folder names are unique among their siblings regardless of case, can't contain `/`, and
are at most 100 characters. Any member can create and rename folders and delete an empty
one. Deleting a folder that still holds decks or subfolders is for **owners and admins**,
and it never deletes a deck: its content moves to its parent, or to `--to <path>`.

| Flag | Meaning |
| --- | --- |
| `--to <path>` | (delete) where the folder's content goes (default: its parent; `/` for the root) |
| `--org <slug>` | the organization to act on |
| `--json` | machine-readable output (default when piped) |

With `--json`:

```jsonc
// folders list
{ "org": null, "folders": [{ "id", "parentId", "name", "path" }] }
// folders create
{ "ok": true, "created": true, "folder": { "id": "…", "path": "Sales/Q4" } }
// folders rename
{ "ok": true, "folder": { "id": "…", "path": "Sales/Q4 2026" } }
// folders delete
{ "ok": true, "deleted": "Sales/Q4", "movedDecks": 3, "movedFolders": 1, "to": "Sales" }
```

`--org` works the same on every cloud command (`push`, `decks`, `folders`, …): explicit
`--org` wins, else the default from `orgs use`, else your personal workspace.

### `pull` and `sync`

Live source sync for a deck folder linked with `push --source`: `pull` merges the cloud
deck's edits into the folder, `sync status` lists who changed what since your last
`sync commit`, and `sync commit` records the folder as a commit crediting the other
editors. All three take `--dir <deck>`, `--org`, `--api` and `--json`.

```bash
liebstoeckel pull                        # merge the live edits into this folder
liebstoeckel sync status --json          # { deckId, base, committed, checkpoints, changed }
liebstoeckel sync commit --json          # { committed, message, checkpoint }
```

`pull --json` returns `{ ok, kind, written, conflicts, head }`, where `kind` is
`in-sync`, `pulled`, `merged` or `conflict`; with conflicts `ok` is false and the exit
code 1. A folder that is not linked yet fails with code `not_linked`.
