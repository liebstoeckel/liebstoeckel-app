`present-relay` is a small Bun server that gives a live session **public reach** beyond the LAN. Its design centers on one rule: **the relay never executes a deck's code.**

## Run a relay

```bash
liebstoeckel relay --port 8080 --tokens <account-token>
# or set PRESENT_RELAY_TOKENS=tok1,tok2 ; serve behind TLS for public use
```

Then present through it from your machine:

```bash
liebstoeckel live my-talk --relay http://localhost:8080 --relay-token <account-token>
```

This uploads the built deck, gets back public presenter/viewer links + QR, and runs the deck's server plugins **locally** (as a privileged peer of the relay).

## How it splits responsibilities

<Steps>

1. **The relay** hosts each session's Yjs `Hub` (authoritative, in-memory, TTL-expired) and **serves the uploaded deck HTML**. Viewers/presenters connect to its WebSocket directly.

2. **Your local machine** rehydrates and runs any **server plugins**, connected to the relay as a privileged "runner" peer, applying their effects to the shared doc. The relay only moves bytes; it never runs deck code.

</Steps>

## Untrusted-HTML isolation

The relay serves the deck on its own origin, but with a response header:

```
Content-Security-Policy: default-src 'none'; script-src 'unsafe-inline';
  connect-src <relay-ws> <relay-http>; frame-ancestors 'none';
  sandbox allow-scripts allow-popups allow-popups-to-escape-sandbox;
```

Omitting `allow-same-origin` puts the deck in a **unique opaque origin**: it can run scripts and sync over WebSocket, but it **cannot reach the relay's cookies, API, or storage**, and each context gets a fresh opaque origin (so decks are isolated from one another too). `allow-popups` is kept for the presenter pop-out and for links that open a new tab; `allow-popups-to-escape-sandbox` makes such a tab an ordinary page (a form there can be sent), while the presenter pop-out is a relay page and gets the sandbox from its own header again. `default-src 'none'` blocks any external fetch, since a built deck inlines all its assets. No separate origin or wildcard certificate needed.

<Aside type="note" title="Plugin implication">
In an opaque origin, `localStorage`/`IndexedDB` throw and cookies are denied. Plugin **client** parts must use WebSocket + shared state only; anything needing secrets or external HTTP belongs in the **server** part (which runs on your machine). WebSocket auth uses the **token in the URL**, so there's no CSWSH risk.
</Aside>

Because storage is blocked, the relay keeps each viewer's participant id (the key their poll vote and Q&A upvotes are recorded under) for them: on a viewer's first load it sets a cookie scoped to that session's page and passes the id to the deck. The cookie holds only that random id, can't be read by the deck, and expires when the session ends. So a reload, or scanning the QR code again on the same phone, comes back as the same participant and doesn't count anyone twice, while an address copied into a chat and opened on another device is a participant of its own. The address never carries an id, and the deck removes one an older link still has.

- Every tab in one browser is the same participant. To try a poll as a second viewer while you rehearse, open the audience link in a private window or another browser.
- A browser that blocks cookies for the relay's host gets a new id on every load, so after a reload its earlier vote no longer shows as its own and it can vote again.
- Decks built with an older version ignore the relay's id and keep it in the tab's address (`?pid=…`), where a copied address shares it; rebuild the deck to change that.

## Legal links on live pages

A relay that serves the public can add a small row to every audience and presenter page
linking your Impressum, your privacy notice and a form to report content. Set all three
(http or https), or none:

| Variable | Link |
| --- | --- |
| `PRESENT_RELAY_LEGAL_IMPRINT_URL` | your Impressum or legal notice |
| `PRESENT_RELAY_LEGAL_PRIVACY_URL` | your privacy notice |
| `PRESENT_RELAY_LEGAL_REPORT_URL` | a form to report content; the session's link is added as `?url=` |

The row sits in the bottom right corner, in English or German by the reader's browser
languages (`?lang=de` or `?lang=en` on the page wins). On a phone it folds into one
**Legal** link at the top right. It is on white-labelled sessions too; on free sessions the
"Published with liebstoeckel" badge joins it in the same pill. On the presenter's page it
shows only in the presenter view (`#presenter`), not in the deck window the room sees. The
links open a new tab. The row is part of the deck's own page, so a deck's code could hide
it; the relay does not guard against that. Without the variables there is no row, and free
sessions show the badge alone as before.

## What the audience downloads

A deck is one file of about 1 MB, and on a phone network that is most of the time between scanning the QR code and voting. The relay keeps it small and sends it once:

- **A copy for the audience.** Viewers get the deck without its slide thumbnails, which only the presenter's overview grid shows. Everything else stays in, including the license notices and the embedded source. The presenter gets the file exactly as built.
- **Compressed.** Pages go out gzip-encoded to every browser that accepts it. The relay compresses each session's audience copy once and adds only the few hundred bytes that differ per viewer for each request, so a room joining at once does not cost it a compression run per phone.
- **Asked for again, not downloaded again.** A viewer's page carries an `ETag` and `Cache-Control: private, no-cache`. The browser keeps it, and a reload, a second scan of the QR code or a phone coming back from another app gets `304 Not Modified` while the talk runs. Every request is still checked first: once the talk has ended, or with a link that is no longer valid, the answer is the usual 403, never the stored page. Presenter pages are never stored (`no-store`).

On the poll demo that is about 390 KB on the wire for a viewer instead of 1 MB.

If you run the relay behind your own proxy (nginx, Caddy, a CDN), let `Content-Encoding`, `ETag` and `If-None-Match` pass through and don't compress `/s/` pages again at the proxy. The `ETag` is weak (`W/"..."`) on purpose, since the same page goes out compressed or not.

## Tokens & quotas

Three token layers keep roles separated:

- **account token**: your deck-runner authenticating to the relay.
- **session tokens**: presenter / viewer roles embedded in public URLs. A presenter link
  is exchanged for a cookie scoped to the session's page on its first load, so the
  token does not stay in the presenter tab's address bar. A deck whose
  [generator stamp](/reference/file-format/#generator-header) names an engine older than
  0.4 (or that has no stamp) keeps its token in the address bar as before, since its
  "drive from your phone" link is built from it. A viewer's cookie holds only
  its participant id and never grants a role.
- **runner token**: the privileged server-plugin peer (WebSocket-only; can't load the page).

The relay enforces per-account quotas (max concurrent sessions, max deck bytes, session TTL, inbound frame caps) and keeps docs in memory only (ephemeral, for privacy).

A session lasts 6 hours unless whoever creates it asks for a length with the
`x-session-ttl-ms` header (milliseconds). The relay keeps a requested length up to 24 hours
and cuts a longer one to 24 hours. Embedding the relay with `createRelay`, `sessionTtlMs`
sets the default and `maxSessionTtlMs` the ceiling; a relay given only `sessionTtlMs` uses
it as the ceiling too.

<Aside type="tip" title="Production">
Local dev is plain `ws://`. For public use, terminate **TLS at a proxy** and pass `--public-url https://…` so links and the WebSocket use `wss://`.
</Aside>
